# ADR-0005. Delta на S3: один писатель на таблицу

**Статус:** принято · 2026-10-16

## Контекст
В лабе 1 бэкфилл `visits_hourly_ingest` сначала шёл с `max_active_runs=3`: три Spark-драйвера
одновременно писали разные партиции одной Delta-таблицы `lake/bronze/visits`.

Что произошло:
1. Первые запуски упали с `ProtocolChangedException`: несколько писателей создавали таблицу в пустом каталоге.
2. После повторной обработки таблица перестала читаться: `DELTA_STATE_RECOVER_ERROR` (в журнале
   нет действия metaData).

Причина: Delta на S3 по умолчанию использует `S3SingleDriverLogStore`. Он корректен только при
одном писателе, потому что S3 не даёт атомарного «создать, если нет» для файлов журнала.
Писатели из разных драйверов могут перезаписать один и тот же `_delta_log/N.json`.
Для нескольких писателей Delta требует внешнюю блокировку (DynamoDB LogStore).

Книга (Incremental Loader, «Обратное заполнение») обещает параллельный бэкфилл, но только
«если хранилище входных данных поддерживает их». Наше для записи — не поддерживает.

## Решение
- DAG'и, которые пишут в Delta, работают с `max_active_runs=1`. Это паттерн Single Runner из гл. 6.
- Сломанная таблица `lake/bronze/visits` оставлена как свидетельство, загрузка переведена на
  `lake/bronze/visits_raw`. Удалить `lake/bronze/visits/` можно вручную.

## Последствия
- Бэкфилл идёт последовательно: 12 партиций ≈ 12 × (время Spark-джобы).
- Чтение параллельное по-прежнему безопасно.
- Если понадобится параллельная запись, нужен LogStore с блокировкой или другой табличный формат.
