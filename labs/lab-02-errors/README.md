# Лабораторная 2. Обработка ошибок в потоке визитов

В таблицах отчёта приведены результаты сохранённых запусков. Для защиты достаточно Word и файлов results.json и spark-results.json.

Из корня репозитория, PowerShell:

    python labs/lab-02-errors/bench.py --sizes 1000 10000 50000 --repeats 3 --seed 42 --batch 250
    ./labs/lab-02-errors/demo.ps1 -Sizes 1000,10000 -Repeats 3 -Seed 42
    python reports/lab-02/make_report.py

Первая команда требует только Python 3.10+. Вторая использует локальные образы первой лабораторной, Docker Desktop, Redpanda и SeaweedFS. Третья использует python-docx и Pillow. Длительность измеряется через perf_counter. Каждый размер задаёт точное число доставок, включая повторные и ошибочные сообщения. Генерация вынесена за пределы времени обработки. SQLite использует временную базу на повтор. Spark получает отдельный топик, DLQ, Delta-пути и checkpoint на эксперимент. Результаты Spark остаются в бакете lake/lab02 и в топиках lab02_* для просмотра через Redpanda Console.

bench.py содержит источник, независимый подсчёт ожидаемых исходов, поштучную обработку и контроль восстановления. Повторный запуск скрипта меняет локальный JSON с измерениями. --out позволяет сохранить альтернативную серию отдельно. demo.ps1 перезаписывает spark-results.json результатами текущей серии. Размеры передаются массивом целых. Для нескольких повторов на стенде допустимо указать один размер несколько раз.

Путь на стенде: publish.py → Kafka (одна партиция на эксперимент) → Spark availableNow → Delta raw → классификация → Delta DLQ и Kafka DLQ, оперативная и исправленные часовые витрины. Порядок событий задаёт Kafka offset. Для контролируемого эксперимента используется относительное модельное время в секундах, event_id — числовой ключ визита. Это отдельный генератор главы 3, оба режима получают одинаковые байты JSON событий. Схема отличается от обычного blogsim; топик visits первой лабы не используется.

Сравнение count по всем часам со словарём генератора обязательно для обеих стратегий. При несовпадении скрипт завершается ошибкой. Выход DLQ — исходное сообщение и причина. Перезапуск Kafka writer по тому же topic вручную может добавить дубли, поэтому сценарий создаёт уникальные топики. Опыт аварийного завершения с незавершённой транзакцией выполнен в SQLite; Spark демонстрирует повторное чтение с checkpoint после штатной остановки. Классификация Spark выполняется по конечной поставке оконными SQL-функциями; ограниченное активное состояние ключей показано отдельно в SQLite.

Дополнительная проверка сохранённых топиков: ./labs/lab-02-errors/verify-dlq.ps1 сравнивает разницу offsets единственной партиции DLQ с числом ошибок JSON и схемы.
